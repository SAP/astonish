# Bot scheduling and Home delivery

Interactive Bot Chat must replace all four generic Chat scheduler tools with `BotScheduleTools` **before** building the final tool list, lexical discovery index, groups and child tool views. Otherwise the generic `schedule_job` declaration instructs the model to ask owner/team and Telegram/email questions and can create an ordinary job rather than a Bot trigger.

The Bot create schema exposes only adaptive scheduling inputs, not delivery, resource-authority, or consent flags. Its default destination is the same Bot's Home report stream. For a bound task mandate, `schedule_job` captures an enabled-by-default request through the trusted `Services.BotAuthorizedOperationFactory`. The issuer persists a bounded, exact source-linked operation after checking the live source lease and mandate pin. The tool returns `pending` and `operation_id`, never an invented job ID or application success. Replay uses run ID plus provider function-call ID; changing the payload under that identity conflicts. Update/pause/remove use the same boundary. The source task mandate is not promoted into recurring authority.

Application is separate: after the source turn terminates, the worker checks current authority/readiness and atomically commits schedule state plus a receipt. Only this committed receipt establishes success and drives Home publication. A permitted enabled target can activate a Draft; Paused/Stopped Bots never implicitly resume, and unrelated disabled jobs remain disabled. A missing issuer fails closed. Legacy unbound turns retain a stateless configuration request explicitly saying no proposal/operation was persisted; they do not claim a job exists. External delivery remains a separate reviewed configuration operation.

`list_scheduled_jobs` validates this Bot's scoped scheduler bindings and reports the actual row's Enabled, NextRun, last status and failure count, not the immutable trigger's intent flag. Missing or mismatched bound rows fail closed; unbound definitions are not reported as enabled.

After review, `syncTriggerSchedules` binds the scheduler row to Bot ID/version/trigger ID (`bot_trigger`). The scheduler admits that Bot occurrence; `WithoutBotTriggerDelivery` prevents the ordinary delivery callback from sending even admission errors externally. The Bot publication pipeline writes the report into Home. Existing separately reviewed external Bot bindings remain supported and are not rewritten by scheduling.

## Unattended final-answer contract

`agent.NewBotPromptOverrides` selects background guidance from typed run metadata; `ChatAgent` applies it to a per-turn system-prompt clone in the production Bot factory/runner path. Autonomous and scheduled runs satisfy “post to this Bot's Home” by returning their final answer. The runtime commits the outcome and `bot.Publisher` publishes it to the existing Home transcript. The model must not search for or invoke a Home-posting tool, ask for recipients, or substitute an external channel. Missing input, denied authority and partial work remain explicit blockers in that final outcome. External delivery still needs separate exact-destination/action authority; reviewed bindings are unchanged.

Background guidance also requires at most one tool call per model response and waiting for its result before the next call. This matches the existing fail-closed serial approval checkpoint (`api.botApprovalCaptureModel`); it neither enables batching nor expands tool permissions. Interactive/control-only conversations and Code mode retain their distinct instructions. Both contracts are hidden system guidance, not appended user text.

`TestBotPromptHomeDeliveryModes`, `TestBotPromptSerialToolGeneration` and `TestBotChatFactoryPromptInjection` cover prompt selection/injection. `TestBotAutonomousFetchFinalHomePublication` drives the real factory, checkpoint, runner, finite 100,000-token meter and SQLite publication with a controlled provider/weather tool: sizable fetch → final answer → committed Home report, replay-safe publication and no external notification. This is controlled execution coverage, not proof of a live model following the guidance. Serial generation is tested as a prompt contract, not attributed as the cause of the Home-post discovery failure.

Regression coverage: `TestInteractiveBotScheduleUsesHomeAdapter` inspects the actual interactive model declaration (failed before the wiring change); `TestInteractiveBostonScheduleReviewedHomeOwnership` invokes that adapter and saves a disabled same-Bot schedule through separate owner review, checking no external binding or legacy delivery callback. `TestBotScheduleProposalCannotSmuggleExternalDelivery` rejects transport changes in schedule proposals without blocking separately reviewed configuration.
