# Chat-first Bot contracts

## Work assessment boundary

Tool-free requirement extraction and candidate assessment set `Config.ResponseJsonSchema` to closed, required-field JSON schemas (including verdict/method enums) and retain the 8,192-token output limit and shared budget. The OpenAI-compatible adapter translates this explicit opt-in into `response_format.type=json_schema` with `strict:true`; Responses API requests use `text.format`. MIME-only ordinary Chat, tools, and provider capability flags remain unchanged. `ResponseSchema` is not used by this path. Proxies/models may reject or ignore schema enforcement: native constrained decoding is not guaranteed by an HTTP 200. Malformed output still fails closed, with no assessment retry or action replay; identity, coverage and evidence validation remain mandatory. Controlled wire tests prove the request contract, not live LiteLLM/Claude enforcement.

Newly claimed work retains a private requirement snapshot. Its conversation uses canonical owner input, questions and run status while draft generation/review/correction remains in the run trace. Only committed assessed output becomes a final Home report; older runs without the work contract retain historical conversational reply reuse. This is not a mandatory owner-review ceremony: quality correction uses existing authority and budgets, and questions remain reserved for genuine missing input or permissions. See [live publication](bot-live-events.md#assessed-work-publication). The older interactive-output mirroring descriptions below describe legacy runs where no work contract is present.

Implementation contract, 2026-11-06. This describes current code, not full release acceptance. The neutral [interaction research](../research/bot-chat-first-ux.md) remains a design study, not a live audit.

## Opt-in authenticated interactive runtime

The new `chat_interactive` execution mode is separate from lifecycle intent. It is admitted only with explicit `BotInteractiveReady` composition, verified authentication evidence and the bounded process-local turn registry. Original caller scopes and live membership—not autonomous `allowed_tools`—bound interactive execution. Legacy control conversations described below retain their existing restricted behavior until composition opts in; an enabled route must not downgrade missing evidence into legacy authority.

Tenant middleware preserves the startup readiness flag and the exact shared turn registry in each request-scoped service bundle, alongside the home provisioner. It must neither derive readiness from request data nor replace the registry; an unready startup remains unready after tenant routing.

The interactive launcher shares Chat catalog registration with strict scoped inputs. Native node tools use the supplied isolated pool. Lazy MCP enumeration is owner-bound and included in the lexical index. Plans use per-agent callbacks; saved flows and distillation dry runs use the host-free flow engine and bound child tools. Scoped workflow adapters reject unbound Fleet/global callbacks; `run_drill`, `inject_drill_credentials` and sandbox-template publication remain explicitly unsupported without scoped composition. No host browser, mailbox, vault or filesystem fallback is installed.

Interactive delegated children preserve the Bot/run identity and original trusted turn authorizer, rechecking Chat authority before discovery/session creation. They do not synthesize an autonomous `RunPolicy`: strict overrides and exclusions narrow the shared wrapped catalog, while public tool preferences only select the initial tools within that ceiling. Child models use the identity-bound shared-budget auxiliary capability (not viewer/request model overrides), with live Chat authorization on each model call. Native and progressive child tools retain the existing exact-once bound invocation handoff. Autonomous children continue to use `RunPolicy.Narrow` unchanged.

`TestBotInteractiveChatHTTPAcceptance`, `TestBotInteractiveAuthorityHTTPAcceptance` and `TestBotInteractiveQuestionHTTPAcceptance` exercise HTTP/SQLite/worker composition with controlled model/node resources. Their presence is not a passing acceptance claim: current integration must pass these before readiness is enabled. External sandbox, provider and MCP services require separate live evidence.

## Minimal creation and durable conversation

For newly created Bots with an omitted or whitespace-only charter, the generated default assigns responsibility for the owner's goals and useful, verified outcomes. Routine work inside the authorized mandate and existing permissions does not require extra review; genuine ambiguity or work outside that scope requires clarification or authorization. Neither a request nor the charter itself grants external-side-effect permissions. Title-first creation prefixes the title only to this generated default. Custom charters are preserved verbatim, including explicit review requirements. Existing persisted charters are not migrated or rewritten; permission defaults, reviewer enforcement, admission, and start behavior are unchanged. `TestBotMinimalCreateDefaults` and `TestBotDefaultCharterHTTPAcceptance` cover defaults, both creation modes, custom/legacy text preservation, and unchanged permissions.

`POST /api/studio/bots` accepts a name and idempotency key without requiring a charter, physical Home or recurrence. With interactive composition, `CreateDraftAndStart` atomically commits the draft/Home, canonical title event, queued `chat_interactive` turn and dispatch. Retries return the same Bot and turn; changed payloads conflict and admission failure rolls back. Model defaults are inherited and missing prerequisites fail closed. Creation starts useful authorized Chat work, not autonomous activation. Source/template/promotion intake and legacy metadata-only creation remain inert unless explicitly started.

`POST /api/studio/bots/{botID}/messages?scope=personal|team` accepts `version`, `idempotency_key`, `instructions`, and supported attachments. Interactive composition selects server-owned `chat_interactive` independently of lifecycle intent. Draft/Paused owner turns do not activate or resume recurrence. Legacy composition still uses Draft → `draft_conversation`, Paused → `conversation`, Active → regular execution with its existing restrictions. Stopped and Deleted reject admission. UI availability is never authority.

Queued/running persisted state drives the existing Chat thinking indicator before tokens and after reload. Waiting questions replace thinking with shared Chat question cards; terminal state clears it. Connectivity is not completion and old replay cannot supersede newer state. Durable `ask_user` uses saved option IDs and supported custom text, never prose parsing; No is input, not permission denial. Lost registry authority requires explicit authenticated continuation preserving the caller ceiling and checkpoint. Retried answers resume the same saved run once. Studio and terminal consume the same contract. The 2026-11-09 owned real-provider journey now passes seventeen checks, including title-first useful work; see the [current evidence boundary](#evidence-boundary). Historical nine-stage receipts are not substituted for that proof, and production external-effect acceptance remains blocked.

Admission atomically commits the run, canonical user event and dispatch outbox. HTTP 202 returns `run`, `home_session_id`, `user_event_id`, and `history_cursor`. An identical retry returns the same receipt; changed payload under the same key conflicts. `presentation=home_interactive` projects interactive turns into ordered durable Home history independently of execution intent. Legacy runs with empty presentation keep their original projection. Clients reconcile canonical events rather than fabricating duplicate echoes. Run traces remain separately inspectable and read-only. These additive JSON fields require no reset, schema regeneration or destructive migration.

## Runtime Home history excerpts

`botConversationSessions.Get` preserves the run session identity/state and adds only Home events preceding the canonical admission ID, excluding current-run mirrors. When that boundary is found, `projectBotHomeHistory` in `pkg/api/bot_home_context.go` makes a copy-on-write model view of paired, non-streaming historical `web_fetch` responses with explicit HTTP 200 status. Only the `WebFetchResult.content` string is excerpted, using Chat's existing `truncateResult` 2,000-byte prefix plus truncation notice (UTF-8 repaired locally). Both ADK's `output` envelope and legacy direct results are supported. Event/call IDs, invocation/branch, call arguments, URL/title/status/warnings, observations and all other fields remain; an explicit excerpt notice identifies the original Home event/call. This is an excerpt, not a semantic findings summary or proof that omitted facts do not exist.

User instructions and model-authored text remain verbatim. No events or call/result pairs are removed. Unknown tools, non-200/unknown statuses, errors, partial/long-running responses and approval/mutation receipts are not reduced. The entire current run—including tool results needed by resumed approvals/questions—is outside this projection. Missing/legacy admission boundaries retain the previous unmodified behavior. Durable Home/run storage, history APIs, Studio/TUI rendering and ordinary Chat are unchanged; excerpts are not persisted or permission data. No extra model call, completion shortcut, intent classifier, or budget change is introduced. This bounds each eligible old fetch body, **not total conversation size**; other large results and accumulated authored history remain subject to normal Chat compaction.

Covered by `TestBotHomeHistoryBoundsOldWeatherPreservesCurrentRun`, `TestBotHomeHistoryProjectionSafety`, and `TestBotHomeHistoryWithoutAdmissionStaysVerbatim`. These scoped tests do not prove live-provider cadence completion or token counts.

## Reviewed control proposals

The restricted proposal capability is not a general mutation tool. `BotControlPayload` is a closed typed union: responsibility, persona, configuration, goal create/edit, memory remember/correct/forget, schedule create/edit/pause/remove, task once, activate and resume. A reason and operation-specific payload are required. Worker identity and lease bind provenance; model prose cannot grant authority.

`/api/studio/bots/{botID}/proposals` exposes durable proposals; `/{proposalID}/decision` accepts only the exact digest and `confirm`/`reject` decision. Records bind Bot, source run/user, immutable version, expected revision, expiry and payload digest. States are `proposed`, `applied`, `rejected`, `expired`, `stale`; confirmation rechecks owner, freshness and operation prerequisites. Applied receipts replay without duplicating effects. `reconciliation_pending` means post-commit reconciliation remains pending, not permission to execute again. Schedule creation does not imply an immediate run; resume does not silently re-enable disabled recurrence. Details retains deterministic direct controls.

Confirmation while the source run is nonterminal or an active writer/teardown barrier remains returns `ErrBotBusy`: HTTP 409 with `Retry-After: 1` and a message to wait briefly and retry the same proposal. No decision receipt is written; the saved digest and proposed card remain retryable. `errors.Is(err, ErrBotConflict)` remains compatible, but busy is checked first in HTTP mapping. Genuine digest/revision conflicts retain their changed-review semantics; this is not a blanket remapping of conflicts.

Before each provider invocation, `pkg/launcher/bot_control_context.go` adds an owner-scoped factual snapshot to a cloned system instruction: live Bot revision/version, up to 20 immutable-version trigger identifiers and schedule facts, and up to 20 proposal receipts ordered by latest creation/decision time. Live owner/version/budget/lease checks bracket the read; a changed revision during retrieval is rejected. Proposal payload prose, trigger instructions, credentials and channel bindings are excluded. JSON string values are data, never grants or instructions. Receipts report stored states without rewriting historical `proposed` tool results or persisting snapshots to conversation history. Unsupported/failed metadata reads are explicitly unavailable, not empty or applied; authorization/fence failures prevent provider dispatch. Omission from this bounded view is not evidence of absence. The existing repository list API still scans proposal activity; only the provider projection is count-bounded.

### Conversational memory targets

The same per-provider snapshot includes up to 20 `memory_targets`, projected from the captured owner's session-prefiltered Bot memory store. Each typed entry contains `memory_id`, bounded category, current Bot `expected_revision`, and `expected_fingerprint` computed by `store.MemoryContentFingerprint` on the complete stored row before redaction. Matching current memory content is rendered separately through `agent.BotMemoryPrompt` as bounded, untrusted factual data; it is not proposal payload prose or control authority. Fresh content supersedes older construction-time snapshots. Superseded records, invalid IDs and rows too large for the factual context budget are omitted, not guessed or truncated into different source contents. Availability and possible omissions are explicit.

The Bot matches an ordinary-language correction to that factual content and copies the exact target metadata into a new reviewed proposal. It asks which fact the owner means if ambiguous, not for internal IDs, fingerprints or JSON. Forget proposals omit content/category; remember proposals omit source identifiers. No new tool, mutation authority, confirmation shortcut, persistence format, Studio event or TUI contract is introduced. Live owner/version/lease and revision checks still bracket retrieval; source fingerprints are rechecked by the existing reviewed mutation protocol.

## Missing tool permission is a separate prerequisite

For autonomous/legacy execution, catalog discovery never grants execution authority. An empty `allowed_tools` remains deny-all; confirming `task_once` does not alter that policy. This historical control-only sequence is not onboarding for explicit `chat_interactive` turns, which use the current caller's scoped Chat authority. An outside-policy denial names the missing tool and requests a separately reviewed configuration proposal in the conversation. It does not create a fake exact-action approval. After the configuration source run finishes, the owner reviews and confirms the immutable scope; only then may a new task proposal be reviewed. An applied failed task is never replayed. Supervised tools may still require a second, exact-action approval. The native smoke's opt-in `CHAT_FIRST_REVIEW_PERMISSION=1` path records the failed predecessor, configuration review, new task review and pending approval separately and does not count this prerequisite as full nine-stage acceptance.

## Source-bound intake and recovery

`POST /api/studio/bots/source-proposals`, `GET .../{proposalID}`, and `POST .../{proposalID}/decision` support Chat, adaptive-task and template review before a Bot exists. Confirmation submits the saved digest, decision and, when required, `reviewed_for_team`; it cannot replace the selected carryover. Only selected summary, memories, goals and text artifacts carry over. Source fingerprints guard freshness; no full source transcript or credentials are implicitly copied. The original Chat remains unchanged; adaptive conversion pauses the original only within successful creation. Destination drafts never autoactivate.

Records persist in the existing private intake store, protected from ordinary unfinished-intake overwrite/delete. Save the proposal ID: GET and identical decision retry recover that exact record. Do not promise a discoverable list of all lost proposals: no source-proposal list route exists. Template confirmation spans team and personal stores: durable `applying` intent plus deterministic destination identity recover the same draft after receipt-write failure; it is not a cross-database atomic transaction. See [reviewed intake](bot-reviewed-intake.md) for full reconciliation and stale-source behavior.

## Approval and continuation

`POST .../approvals/{approvalID}/approve-and-continue` combines exact action approval with checkpoint continuation. The saved action digest and persisted checkpoint remain authoritative; typed question responses must match their saved question. It neither approves unrelated actions nor activates a paused Bot. Legacy `/decision` and run-resume endpoints remain available: the legacy approval decision alone does not enqueue continuation. A combined receipt must not be mistaken for a broad grant.

## Compact Studio and terminal

New Bot opens the existing Chat transcript/composer and artifact harness with identity/status and a Details control. Bots and Chats remain separate sidebar sections. No permanent Thread/Runs/Goals/Schedule/Memory tab bar or setup wizard is required for conversation. Details contains execution setup, run/activity inspection, review inbox, goals, schedule, memory and configuration. Closing Details preserves unfinished edits while the Bot stays mounted; leaving the Bot is not durable form storage.

Empty conversations invite a responsibility/task; loading and failed snapshot reads show status and retry; populated conversations prioritize chronological replies and inline review references. Review cards re-fetch authoritative records and disable decisions when reads fail; transcript text itself is never an executable grant. Stopped/Deleted and non-authorized views remain read-only. Background scheduled results remain distinguishable from interactive turns. Existing Chat report, artifact and tool rendering is reused.

Terminal Home input uses `/messages` for Draft/Paused/Active, preserves rejected input and idempotent retry, and watches the canonical Home stream. `/bots proposals` exposes exact saved reviews; approvals use the combined operation where supported. The explicit `run`, `test-once`, `conversation`, legacy approval and resume CLI contracts remain compatible. Bare local Code does not gain a Bot worker.

## Evidence boundary

The strict driver requires the Chat-first HTTP admission/reopen, proposal/source-intake, workspace and ordered-conversation browser tests, plus terminal parity and legacy compatibility tests. Controlled browser and PTY fixtures prove client behavior, not a real provider or deployed sandbox. The production-worker HTTP test uses a controlled model. Driver regression tests prove gate wiring and fail-closed accounting, not execution of those selected suites.

The [2026-11-09 seventeen-check proof](bot-release-checklist.md#employee-operations-final-gate-boundary--2026-11-09) is current owned daemon/provider/Docker evidence: `.tmp/employee-writer-live.md` records launcher exit 0 and exact candidate/Bot/Home identity; `.tmp/employee-writer-final-status.json` and `employee-writer-final-receipts.json` record 17/17, not fourteen. Read-only canonical writer observations verify restart/pause, denied memory preservation, one newly approved local retirement, and hard deletion with peer/volume preservation. The next decision is a reviewed bounded provider/resource adapter plus durable key/receipt and supported approval UI-to-worker integration, not arbitrary external authority. Direct Kubernetes and the full isolated deployment gates remain unverified; user daemon and Kubernetes resources were untouched. No phase or release is closed by this documentation reconciliation.
