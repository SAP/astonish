## Security and replay contract

- The common Bot handler validates authenticated principal/tenant scope, bounded strict JSON and IDs. Personal/team selection uses the existing scoped repository; IDs do not grant access and there is no fallback between scopes.
- `AuthorizeBotHomeSetup` performs live owner/admin edit authorization, requires a draft without active-run/lease markers and checks the expected revision. Anonymous, foreign-scope and reader requests fail before storage provisioning. Owner identity comes from the stored Bot, not request JSON.
- `BotWorker.provisionHome` authenticates the stored owner against current user/organization/team membership. `BotHomeManager.Provision` checks the owner principal and current Bot before calling the configured backend. The returned binding must validate and match the exact derived organization/team/user/Bot scope.
- Only trusted daemon composition creates the narrow internal `bots:home:register` service context. It discards inherited context values and uses the exact backend result in its verifier. `Services.BotHomeSetup` is installed after worker construction and before Studio registration; tenant middleware preserves this callback in request-scoped services. An absent callback/backend fails closed with `503`.
- The server derives binding identity from Bot ID and the original setup revision. Exact lost-response retry at that revision converges only on the same binding; retry at the current revision is also a no-op. An intervening configuration edit is not a lost-response retry and conflicts. Backend validation/ensure may still occur on a retry: idempotence does not mean zero external calls.
- Caller and owner active identity/membership are rechecked after external provisioning. Public setup additionally passes a trusted `BotHomeRegistrationAuthorization`: registration reauthorizes the original requesting editor and runs the live identity/membership validator inside the binding transaction, before either persistence or replay success. The service principal alone is not public setup authority. Existing internal registry callers remain compatible without this optional authorization object. Membership lives in separate platform/org stores; these checks do not claim a distributed serializable transaction or lock revocation through commit.
- A failed registration CAS never deletes storage, because a concurrent request may already use the same physical resource. An unregistered resource is retained for safe retry or administrative reconciliation; this is not evidence of automatic orphan cleanup. Normal registered-home retention/cleanup is documented in [bot-home-retention.md](bot-home-retention.md).

`400` rejects invalid/unknown fields (including client storage paths); `401` is missing identity, `403` forbidden access, `404` a scoped miss, `409` stale revision/ineligible lifecycle/binding conflict, and `503` unavailable capability. Refresh/review after a conflict; do not blindly activate or retry execution to work around failed setup.
