# Bot skill inspection and explicit legacy import

Studio Details → Skills & history reads committed skill records, revisions, and run receipts. Unsupported schema versions are not interpreted. Failed refreshes retain visibly stale data and disable selection; pagination uses server cursors. Opening and closing inspection does not admit work or alter grants, schedules, or the Home draft.

Review legacy import is a separate opt-in flow: read the pinned Bot version, select a legacy procedure, then confirm. Cancel performs no write. Confirmation posts `/api/studio/bots/{botID}/skills/import-legacy` with scope, `expected_revision`, `trigger_id`, `version`, SHA-256 `instructions_digest`, and a stable per-confirmation `idempotency_key`. The server owns authorization and stale-version checks. Import creates draft knowledge only and leaves schedules and grants unchanged. Failures are shown as unconfirmed, not successful imports.

Terminal `/bots skills` remains read-only (legacy import is Studio-only); `/skills` remains unrelated local knowledge. Escape preserves the selected Bot and unfinished work. Revert revision pointers render their numeric value only when present.

`python3 tests/e2eboot/bot_skill_surface_acceptance.py --browser --terminal` is the approved compatibility entrypoint; it delegates to `tests/e2eboot/skill_surface_acceptance.py` and always requires all 14 cases (8 browser, 6 PTY), even when flags are omitted. The canonical validator tests remain in `tests/e2eboot/skill_surface_acceptance_test.py`; wrapper coverage is in `tests/e2eboot/bot_skill_surface_acceptance_test.py`. Browser cases exercise real scoped handlers and isolated SQLite; unsupported-schema injection and PTY HTTP responses are controlled fixtures, not proof of daemon scheduling or real-provider behavior. The gate rejects missing markers, skipped tests, and failing tests.

## Schedule task binding

`pkg/launcher/bot_schedule_tools.go:addSkill` keeps saved methods optional for ordinary instruction-based schedules. If an invocation label accompanies explicit task instructions without an explicit skill ID or persisted current skill selection, preserve those instructions and clear the unbound invocation; do not demand skill creation or a separate review merely because the method is absent. Invocation-only requests still need an unambiguous persisted selection. Explicit skill IDs remain scoped to this Bot, and selected methods retain thin invocation bindings rather than copied procedure bytes. This changes no mandate, minimum interval, budget, enqueue/commit, or exact-operation authorization checks. `TestBotAuthorizedScheduleHTTPAcceptance` exercises both personal direct-tool and team `execute_tool` capture with no saved method, pending source acknowledgment, one applied receipt and no approvals.

## Optional runtime read authorization

The production mandate already includes `bot_skill_list` and `bot_skill_read`. `BotCatalogueClassifier` classifies only these scoped first-party method inspections as verified local reads, just like fenced work/evidence inspection. An empty list or missing method returns normal optional-tool feedback rather than requesting owner approval. The policy allowlist, explicit denials, live lease/budget checks and Bot-scoped repository lookups still apply; foreign MCP/request identities cannot borrow this classification. `bot_skill_use` and `bot_skill_save` remain reversible writes, and child-session mutation denial is unchanged. `TestBotOptionalSkillReadNoApprovalHTTP` exercises real HTTP admission and the production worker/factory for personal native dispatch and team `execute_tool`, checking empty-list/missing-read feedback, a useful final answer, no created skills and no approvals. `TestBotSkillReadClassificationPreservesPolicyCeilings` covers classification, denials and foreign identities.
