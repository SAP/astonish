# Kubernetes retained Bot home foundation

Direct Kubernetes sandboxes optionally bind a durable Bot home independently of the session overlay. This is not enabled for ordinary chat, flow, fleet, or template-builder sessions.

## Configuration and storage

Set `sandbox.kubernetes.homes_pvc_name` to an **independent** operator-provisioned RWX PVC in the sandbox namespace. Empty means disabled; binding requests then fail with `ErrBotHomeUnsupported`, rather than falling back to ephemeral storage. The claim must differ from layers and uppers. `EnsureBotHome` verifies claim existence and issues an opaque versioned reference derived from namespace, claim, and `BotHomeScope.Key()` (SHA-256 of unambiguously encoded org/team/user/Bot IDs). IDs never become filesystem path segments.

Helm exposes `sandbox.storage.homes.enabled` (default false), `pvcName`, `existingClaim`, `size`, and `accessMode`. New claims have `helm.sh/resource-policy: keep`. An existing claim is referenced, not managed. Operators must also retain the PV/backing storage and namespace: Helm's keep annotation does **not** protect data from explicit namespace/PVC deletion or a storage administrator. Back up retained homes separately from template/upper stores.

## Runtime isolation and lifecycle

`SessionSpec.BotHome` is validated against the configured backend, namespace, claim, and scope. A retained session has an immutable ConfigMap named from its session hash containing its binding; this is control-plane metadata, never mounted into the workload. Kubernetes RBAC requires ConfigMap get/create/update/delete in the sandbox namespace (deploy the updated Role alongside the binary). Metadata survives pod eviction and daemon restart, and allows `StartSession` to restore the same home without a caller supplying it. A different or missing binding on repeated `CreateSession` fails closed. Existing ordinary sessions cannot be upgraded in place. Existing pod annotations **and volume/subpath declarations** are checked before adoption.

The init container mounts only `<scope-hash>/`, never the claim root. It initializes `data/` to root:root, mode 0700 once, with an owner marker outside data. It rejects symlinks, conflicting ownership, and nonempty unowned data. Interrupted initialization fails closed for operator review. Repeated initialization validates ownership without recursive chown, permission resets, or copying template files. The workload mounts only `<scope-hash>/data` at `/mnt/astonish-bot-home`, not the marker or other homes. Service-account token automount is disabled for retained workloads.

The canonical entrypoint (`pkg/sandbox/k8s/overlay_entrypoint.go`, regenerated by `make sandbox-entrypoint`) requires the actual volume mount and bind-mounts it at `/sandbox/rootfs/root` **after overlay composition and before chroot**. HOME is fixed to `/root`; arbitrary source/destination paths are not supported. Symlink targets and missing mounts fail startup. The bind lives outside upperdir, so existing upper eviction and template capture pipelines do not serialize retained data. Nil bindings leave the existing three-volume emptyDir-overlay manifest unchanged.

`DestroySession` removes the pod, upper state, registry entry, and session ConfigMap only. It does not delete the homes PVC or scoped home.

## Durable attachment admission (purge prerequisite)

Every retained `CreateSession`, `StartSession`/eviction recovery, and offline reader reserves admission **before submitting a mounting pod** in a per-home `astn-home-fence-*` ConfigMap. Its full binding is validated, and Kubernetes resourceVersion CAS serializes changes across backend instances. The record has no owner references, expiry or TTL. Nil-home sessions do not access it. This is shared attachment admission, not a single-writer lock: multiple sessions/readers may use an active home.

Each invocation owns a random token recording its physical pod name and whether creation remains pending. Only that invocation can settle its token after successful creation/adoption. Completed attempts for a pod name coalesce; another worker's pending token is never stolen. A typed **local manifest rejection before any pod create is submitted** lets that invocation cancel only its own pending token, using resourceVersion CAS and a bounded cleanup context independent of request cancellation. This also applies to nested create/recovery invocations; older pending tokens remain untouched. Correcting the manifest and retrying therefore does not leave an unused admission blocking later destroy/purge. Failed cancellation remains an error and leaves the fence conservative. Offline readers already validate binding, path, and limit before reserving.

Crashes, API create ambiguity (including cancellation returned by a submitted create), post-create validation/registry failures, and other unproven failures can deliberately strand reservations. Observing no pod is NOT permission to expire a pending token: a paused worker or delayed API request could still mount later. Operator repair requires quiescing all possible creators and resolving in-flight API requests, not simply deleting old records.

`DestroySession` and reader cleanup release settled reservations only after GET confirms pod NotFound. Delete acknowledgement, a finalizer-held pod, lookup failure, cleanup failure or any unresolved token prevents release. Stop/eviction conservatively retain the reservation; successful recovery coalesces completed attempts. The fence survives destruction of the session metadata. ConfigMaps must be retained/backed up and **not** garbage-collected by age. Pre-upgrade workloads and older daemons do not participate: a future purge rollout must quiesce/drain them and adopt their evidence before trusting this ledger.

The typed `active`, `deleting` and `deleted` states are validated; both terminal admission states reject session creation, recovery, readers and `EnsureBotHome`. `DeleteBotHome` CAS-transitions an **existing** active fence with zero reservations to deleting. Missing fence evidence fails closed; deletion never creates it. Terminal tombstones are retained permanently and are never reopened.

## Offline artifacts and purge boundary

`ReadBotHomeArtifact` implements the optional artifact capability without a running session. It validates the exact backend-issued binding, canonical relative path and a positive limit no larger than 16 MiB before any Kubernetes request. A unique read-only helper mounts only `<scope-hash>/`, never the shared claim root. It has no init container, overlay, session registration, service-account token or provisioning command; it uses the existing sandbox image's shell/coreutils and existing Kubernetes exec transport. The helper checks the owner marker outside `data/`, resolves containment, opens the file, rechecks containment and regular-file type through its own `/proc` descriptor, and bounds both file output and transport buffering. Invalid owners, missing files, escaping links, directories and oversized output fail closed. This is not a transactional snapshot of concurrent workload writes.

Helpers have a two-minute context and pod active deadline. Cleanup uses an independent ten-second context on success, error and cancellation, with UID preconditions after successful creation; cleanup errors are returned, not silently hidden. A deadline bounds execution but is not a TTL controller: operator reconciliation may be needed if API deletion fails or the daemon crashes. Helpers never enter the ordinary session registry. Admission-mutated storage mounts and replacement pods are rejected before exec.

**Authorized logical data purge is implemented.** The existing fence atomically records a random operation/helper name and image before any helper submission. Only that CAS winner may issue Create, once. Concurrent callers and crash retries only adopt the exact recorded pod with validated command/mounts and then UID; they never resubmit Create, even for NotFound. Ambiguous creation or a crash before submission can therefore strand deleting and requires operator reconciliation after quiescing possible creators. Failed helpers are not automatically replaced. This conservative limitation prevents two destructive helpers or late creation after terminal success.

The nonprivileged helper mounts only the scope root and requires its exact `.owner` before touching data; an absent owner is never adopted. It runs the purge as its main process (not an exec request), so Kubernetes terminal status survives daemon crashes. It rejects symlinked data roots and nested mounts, uses physical `find -P -xdev -depth -delete`, and never follows links or accesses the claim root. Intent and completion markers are atomically renamed and synced. A crash after data removal but before receipt publication is script-idempotent for the same operation. The API records successful termination and UID before deleting the helper, requires GET NotFound before marking deleted, and returns cleanup/API errors with the fence still deleting. A retry can complete cleanup without another destructive command.

This is **logical purge of `data/`, not physical scope-directory removal or secure erasure**. The scoped mount root remains with `.owner` and `.purged` (operation ID); an interrupted pre-intent write can also leave `.purge-*` temporary metadata, and other preexisting scope metadata is not removed. The per-home fence retains binding, state and operation receipt. Kubelet may create a missing scope subpath; in that case missing `.owner` makes purge fail, never succeed. No owner or data directory is provisioned by deletion. A scope-only helper cannot remove its own mount root. No host-file fallback or claim-root helper is used.

For offline reads of an absent scope, kubelet may likewise leave an empty scope directory; the helper never writes an owner marker or `data/`, and rejects the missing owner. No missing home is adopted.

## Verification boundary

`go test ./pkg/sandbox/k8s -run TestBotHome` covers configuration/factory wiring, scope separation, unsafe references, manifests, existing-pod conflicts, immutable session recovery, retained-claim preservation, init filesystem safety, canonical entrypoint inclusion, and Helm opt-in/existing-claim rendering. These are not live mount/durability proof. Unit init tests substitute only the mount path and root chown syscall to run unprivileged.

Live acceptance requires an already authorized test cluster, RWX claim, current sandbox image generated with the new entrypoint, and usable overlay runtime: create a Bot session, write files under its actual chroot `$HOME`, record mount evidence, destroy/recreate its pod and then its session, verify the same files from a new run, verify a different scope cannot see them, and inspect an ordinary sandbox for unchanged behavior. No cluster is provisioned by these tests.

### Offline helper local verification

- Failing-first `TestBotHomeOfflineCapability` reported `missing offline artifact capability` before implementation.
- `KUBECONFIG= go test ./pkg/sandbox/k8s -count=1` passed after implementation.
- `KUBECONFIG= go test ./pkg/sandbox/k8s -run TestBotHomeOffline -count=1 -v` passed fake API/exec tests for successful bounded read, oversized transport, exec rejection, cancellation cleanup, foreign mount rejection, cleanup failure, and pre-API binding/path/limit validation.
- `ASTONISH_BOT_HOME_READER_TEST_IMAGE=ghcr.io/sap/astonish-sandbox-base:dev go test ./pkg/sandbox/k8s -run '^TestBotHomeOfflineReadFilesystem$' -count=1 -v` passed on this macOS host using isolated, network-disabled Docker containers running the production Linux shell command. It exercised retained bytes, wrong/missing owner, escaping links, oversized files, directories and FIFOs. This proves filesystem checks, not Kubernetes orchestration.
- No live Kubernetes helper was launched. Kubelet read-only subpath behavior, real SPDY cancellation, admission compatibility, driver permissions and eventual pod removal remain unverified. Safe purge was unsupported at that stage; the subsequent logical-purge implementation and verification are recorded below.

### Attachment prerequisite local verification

- `KUBECONFIG= go test -race ./pkg/sandbox/k8s -run 'TestBotHomeAttachment|TestBotHomeOfflineReadCleanup|TestBotHomeHelm' -count=1` passed. Two backend instances share a fake API with explicit resourceVersion conflict enforcement; tests exercise concurrent creates, reservation-before-pod ordering, CAS retry, recovery, foreign binding, terminal-state rejection, denied admission, ambiguous session/helper creation and finalizer-held deletion.
- `KUBECONFIG= go test ./pkg/sandbox/k8s -count=1` passed after wiring; Helm verifies the ConfigMap update permission required for CAS. Reader cleanup tests assert reservations survive deletion errors and are removed only on observed absence.
- No live cluster, physical unmount, crash/restart process drill or storage removal was exercised. Pending reservations intentionally require safe operator reconciliation; automatic reclamation remains unsupported. Production deletion transitions were added subsequently (below).

### Logical purge verification

- Failing-first `TestBotHomePurgeCapability` failed with `missing retained-data purge capability` before implementation.
- `KUBECONFIG= go test -race ./pkg/sandbox/k8s -run 'TestBotHomePurge|TestBotHomeAttachment' -count=1` verifies two-instance CAS admission/purge races, pending reservations, missing fences, terminal Ensure rejection, helper failure, cleanup error/finalizer retry, and ambiguous create adoption without resubmission.
- `KUBECONFIG= go test ./pkg/sandbox/k8s -count=1` passed.
- `ASTONISH_BOT_HOME_PURGE_TEST_IMAGE=ghcr.io/sap/astonish-sandbox-base:dev go test ./pkg/sandbox/k8s -run '^TestBotHomePurgeFilesystem$' -count=1 -v` passed actual Linux script tests for data removal, unchanged outside symlink targets, missing/wrong ownership, data-root symlink rejection, repeated completion and interrupted receipt recovery.
- Nested bind-mount setup failed on this Docker host (`mount ... bind /outside failed`); that case now requires `ASTONISH_BOT_HOME_PURGE_MOUNT_TEST=1` and is not claimed verified. No live Kubernetes helper, CSI behavior, physical unmount or daemon process-crash drill was exercised. Failed or absent ambiguous helpers intentionally require safe operator intervention; retries never launch replacement purge pods.

### Recorded local verification

- `KUBECONFIG= go test ./pkg/sandbox/k8s -count=1` passed, including the Helm tests (not skipped).
- `KUBECONFIG= go test ./pkg/sandbox/k8s -run TestBotHome -count=1 -v` passed. Recovery negatives include claim-root/traversal/expression mounts, initializer isolation, token automount, incorrect HOME/mode, corrupt metadata, and attempted ordinary-session upgrades.
- `make sandbox-entrypoint` regenerated the canonical image input; `sh -n astonish-sandbox-entrypoint` passed. No sandbox image was built or deployed.
- `kubectl config current-context` returned `current-context is not set`. Actual kubelet subpath creation, storage-driver permissions/root-squash behavior, bind mounts in each overlay mode, live file persistence, cross-scope visibility, and ordinary live sandbox behavior remain unverified.

The immutable session ConfigMap is required recovery state: retain and back it up together with the session registry. Loss of both pod and ConfigMap removes the backend's evidence that a session had a retained binding; this foundation does not reconstruct deleted control-plane metadata from home contents. Scoped mounts do not strengthen the existing privileged direct-Kubernetes sandbox threat model into a hostile-workload security boundary.
