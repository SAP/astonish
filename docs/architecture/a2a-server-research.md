# A2A Protocol Integration — Research & Architecture Decision

## Executive Summary

This document captures the research findings on the A2A (Agent-to-Agent) protocol and the architectural decision to implement Astonish as an A2A Server using the existing Channel adapter pattern.

**Decision: Implement A2A Server as a Channel adapter (`pkg/channels/a2a/`). Defer A2A Client to a future initiative.**

## What is A2A?

The **Agent-to-Agent (A2A) Protocol** is an open standard created by Google Cloud (April 2025), now governed by the Linux Foundation (June 2025, 150+ contributing organizations). Version 1.0.0 was released March 2026.

A2A enables AI agents built on different frameworks, by different vendors, to communicate and collaborate as **peers** — not merely as tools. It complements Anthropic's MCP (Model Context Protocol): MCP standardizes agent↔tool connections, A2A standardizes agent↔agent collaboration.

### Key Technical Details

- **Transport**: HTTP/HTTPS with JSON-RPC 2.0 (primary), also gRPC and REST bindings
- **Streaming**: Server-Sent Events (SSE) for real-time updates
- **Async**: Push notifications via webhook callbacks
- **Discovery**: Agent Card at `/.well-known/agent-card.json`
- **Auth**: OpenAPI-style security schemes (Bearer, API Key, OAuth 2.0, OIDC, mTLS)
- **Official Go SDK**: `github.com/a2aproject/a2a-go/v2` (A2A v1.0 compliant, Apache 2.0)

### Core Concepts

| Concept | Description |
|---|---|
| **Agent Card** | JSON metadata describing identity, capabilities, skills, auth requirements |
| **Task** | Unit of work with a rich state machine (9 states) |
| **Message** | Communication turn with role (user/agent) containing Parts |
| **Part** | Content unit: Text, File, or structured Data (JSON) |
| **Artifact** | Output generated by the agent (documents, images, data) |
| **Skill** | Specific capability advertised in the Agent Card |

### Task States

`SUBMITTED` → `WORKING` → `COMPLETED` / `FAILED` / `CANCELED` / `REJECTED`
                        → `INPUT_REQUIRED` (multi-turn) → `WORKING` → ...
                        → `AUTH_REQUIRED` → `WORKING` → ...

### A2A vs MCP

| Dimension | MCP | A2A |
|---|---|---|
| Relationship | Agent ↔ Tool/Data | Agent ↔ Agent |
| Core purpose | Extend what one agent can do | Enable agents to collaborate |
| Workflow unit | Tool calls | Task lifecycles |
| Opacity | Agent sees tool internals | Agents are opaque to each other |

## Why Channel is the Right Pattern (Server Role)

### The fit

The A2A Server role maps directly to Astonish's `Channel` interface:

1. **External platform sends message** → External agent sends `SendMessage` via JSON-RPC
2. **Adapter normalizes** → A2A Parts extracted into `InboundMessage`
3. **Router determines session** → `contextId` maps to session key
4. **ChatAgent processes** → Same processing pipeline as any channel
5. **Response delivered** → Wrapped as A2A Task result (sync, SSE, or push callback)

### Where the metaphor holds perfectly

- Inbound message normalization ✓
- Session-per-conversation ✓
- Routing through ChannelManager ✓
- Credential redaction on outbound ✓
- Typing indicators (→ WORKING state events) ✓
- Multi-tenant resolution via PlatformResolver ✓
- Allowlist-based access control ✓

### Where A2A extends beyond typical channels

| Extension | How we handle it |
|---|---|
| Rich task lifecycle (9 states) | TaskStore in `pkg/a2a/` manages state machine; adapter maps terminal states to response delivery |
| Async callbacks | PushNotifier component delivers results to client webhooks after processing completes |
| Agent Card discovery | New HTTP endpoint in `pkg/api/` — not a channel concern, but enables the channel |
| Streaming with state semantics | Reuse existing SSE infrastructure, wrap events in JSON-RPC format |
| Multi-turn via INPUT_REQUIRED | Maps to agent asking clarification questions — adapter detects and sets appropriate task state |

### Why NOT a separate subsystem

Treating A2A as something entirely different from channels would mean:
- Duplicating the routing logic
- Duplicating session management
- Duplicating credential redaction
- Duplicating fleet integration
- Duplicating the ChatAgent invocation pipeline

The channel pattern gives us all of this for free. The A2A-specific concerns (task state machine, push notifications, Agent Card) are additive layers, not replacements.

## Scope: Server Only

**In scope (this initiative):**
- A2A Server: receive tasks from external agents
- Agent Card: advertise Astonish capabilities
- Task lifecycle: manage state machine for incoming tasks
- Push notifications: async callback delivery
- Streaming: SSE response streaming
- Multi-turn: INPUT_REQUIRED state handling
- Authentication: validate external agent credentials
- Multi-tenant: map agent identity to team context

**Out of scope (future initiative):**
- A2A Client: Astonish calling external agents
- Agent discovery: finding and connecting to remote agents
- `delegate_to_agent` tool: LLM-driven delegation to external agents
- Agent registry: catalog of known external agents

The server role already provides **two-way communication** within a task:
- Client sends message → Server processes → Server returns result (sync or async callback)
- Multi-turn: Server requests input → Client provides → Server continues

This is complete bidirectional interaction. The "client" role is about Astonish *initiating* tasks to other agents — a fundamentally different concern.

## Implementation Plan (High-Level)

### Phase 1: Protocol Foundation (`pkg/a2a/`)
- A2A types (using official Go SDK as foundation)
- Task state machine and TaskStore
- Agent Card builder

### Phase 2: Channel Adapter (`pkg/channels/a2a/`)
- `A2AChannel` implementing `Channel` interface
- Message normalization (Parts → InboundMessage, OutboundMessage → Task result)
- Session key mapping (contextId ↔ Astonish sessions)

### Phase 3: HTTP Layer (`pkg/api/`)
- Agent Card endpoint (`/.well-known/agent-card.json`)
- JSON-RPC handler (synchronous `message/send`)
- SSE streaming handler (`message/stream`)
- A2A authentication middleware

### Phase 4: Async & Push
- Push notification registration and delivery
- Background task processing
- Task polling endpoint (`tasks/get`)

### Phase 5: Multi-Tenant Integration
- Agent identity registration (admin CLI/API)
- PlatformResolver integration for A2A identities
- Per-team skill exposure in Agent Card
- Rate limiting per agent identity

## Technology Choices

| Choice | Rationale |
|---|---|
| `a2aproject/a2a-go/v2` | Official SDK, A2A v1.0 compliant, Apache 2.0, multi-transport |
| JSON-RPC 2.0 (primary) | A2A spec's primary binding; simplest HTTP integration |
| Existing SSE infra | Astonish already streams via SSE for Studio Chat |
| In-memory TaskStore (personal) | Simple, no extra deps for single-user mode |
| DB-backed TaskStore (platform) | Durability, audit, multi-instance support |

## Ecosystem Context

Major platforms already integrating A2A:
- Salesforce (Agentforce), ServiceNow, SAP (Joule), Google Cloud (ADK/Agentspace)
- LangChain, Atlassian (Rovo), PayPal, UiPath, NVIDIA
- 150+ organizations in the Linux Foundation governance

Implementing A2A Server makes Astonish **discoverable and callable** by any agent in this ecosystem — a significant interoperability advantage.
