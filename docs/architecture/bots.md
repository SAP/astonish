# Bots inside Chat

## Durable work requirements (implementation in progress)

First claims now pin the saved assignment, charter and goal identities/revisions into the private run JSON envelope. `BotWorkStore` reads and updates this state only under the current scoped worker identity, live lease and revision CAS. Reads return detached copies; updates cannot replace source requirements or rewrite an already submitted candidate. Public run JSON does not expose the private work record. Existing reports and in-flight legacy continuations are not retroactively assessed.

The bounded state machine is preparing → producing → candidate-ready → reviewing → accepted, with reviewing → repair-ready → repairing → candidate-ready for at most two corrections. Missing evidence or limits produce blocked work; recovery records interruption without replaying effects. Criteria retain source references and exclusions of unrelated goals require reasons. Assignment and charter cannot be excluded. The assessment input limit is 32 KiB of source contract, 64 criteria and 1 MiB of candidate content; oversized sources are retained with an explicit blocker, never silently dropped to obtain a pass.

Internal work preparation and review calls carry a typed `bot.ModelCallPurposeAssessment` context value. Launcher reads it before owner rebinding and omits only producer control-prompt enrichment; the assessor system remains exact. Both live binding checks, owner scope, isolation, the wrapped provider and shared run budget remain unchanged. Purpose is not an authorization grant and is never inferred from prompt text.

Candidate digests bind actual captured text, artifact bytes and observation references. Semantic model assessment is distinct from mechanical observation and is not an authorization grant or factual proof. Successful runtime/tool execution alone is not an assessment. The optional public `BotReport.Quality` contract is additive; absent quality means not assessed. Run-owned work is retained and purged with its existing run envelope, without new tables, schema migration, global skill storage or separate retention machinery.

At this stage only persistence and validation are implemented. The review controller, publication enforcement and Studio/terminal projection remain subsequent implementation phases; this section does not claim live employee-quality acceptance or close earlier release limitations.

## Architecture and ownership

Bots are daemon-hosted, persistent assistants built around the existing wired ChatAgent and ChatRunner. They do not introduce another model loop, tool catalog, scheduler, transcript store or authentication system. Personal Bots belong to one user; team Bots belong to the team with an accountable owner. The scoped store and authenticated principal establish ownership; IDs supplied by callers do not.

`pkg/store/bots.go` defines schema-versioned snapshots, runs, exact-action approvals, activity projections, read cursors and the aggregate repository. UUIDs identify Bots, runs and home/run conversations. Session names are not authorization. Separate sessions retain the home conversation and each run transcript. Bot activity is a monotonically ordered control-plane projection, not a duplicate tool transcript. Thread results, run state, approval counts and unread badges must derive from the same persisted activity and session records.

`pkg/bot/runtime.go` defines Runtime, HomeManager, ModelResolver, Clock, Notifier and error contracts. The runtime design reuses existing Chat execution; this package cannot depend on API or launcher. Fresh physical containers and retained home mounts are later-phase runtime obligations, not capabilities of the Phase 2 registration seam. Storage retention is not a backup. Filesystem projections do not grant authority or replace versioned records.

## Lifecycle

- Draft activates only after reviewed explicit activation. One-time tests and recurring activation are separate consent.
- Active can pause or stop. Paused/stopped resumes only explicitly; no missed runs replay by default.
- Pause rejects autonomous admission immediately and fences execution before its next action. It cannot reverse an already committed external effect. Owner conversation and review remain available; autonomous tools require resume.
- The compatibility soft-delete API preserves previous state and home/history for 30 days. Restore returns paused, not active; at or after expiry restoration is rejected.
- Studio deletion is owner-only and permanent in both scopes: explicit confirmation admits irreversible intent, fences work and disables schedules. It has no restore window. Pending cleanup stays visible as pending until verified exact-target purge; a 202 is not completion.
- Purge requires cancelled/fenced work and completed external cleanup, all recorded durably. Retention must expire for soft deletion; permanent intent sets only this Bot's deadline to now and uses exact-target purge rather than a batch sweep.
- Closing a browser, pressing Escape or detaching a terminal is not a lifecycle action.

Run transitions are validated by `ValidateRunTransition`: queued -> running/skipped/cancelled; running -> waiting approval/interrupted/terminal; waiting approval or interrupted -> queued only with active Bot, current authority and safe checkpoint, otherwise partial/cancelled. Terminal states cannot restart themselves. A new request is a new run. Transport `done` never means succeeded.

Approvals transition pending -> approved/denied/revoked/expired; approved -> consumed/revoked/expired. No decision can resurrect consumed, denied or expired authority. Approval alone does not resume a paused Bot. Consumption must atomically compare run/version/action digest/expiry/revocation and live fencing token immediately before execution.

Goals represent durable active/completed outcomes. Tracked items represent open/blocked/completed/cancelled commitments. Run todos are separate: at most 25, unique IDs, at most one in progress, and exactly one during actionable work. Completed work requires attributed primary observation or owner confirmation, not inference. Blocked work names its unblock condition.

## Permission and budget contract

`pkg/execution/run_policy.go` defines immutable request-scoped policies and exact executable identities. Runtime adapters install a BotRunIdentity plus the existing authenticated Principal. Missing/mismatched identity, principal or policy fails closed. Ordinary execution without Bot identity/policy remains unchanged.

Explicit denial wins. Child internal policies intersect the parent; public delegation preferences never widen authority. Children receive no grants and cannot perform consequential effects such as send/spend. Mechanically checked reads and reversible writes may proceed according to autonomy; unknown/unverified effects require review. Descriptions, HTTP methods, memory, external pages and model confidence are not effect classification. ConstraintsVerified is set by trusted adapters only, never accepted from JSON.

Action digests bind canonical JSON arguments, tool identity, effect, recipient, merchant, currency and spend amount. Arguments carry credential references, not resolved secrets. A matching grant returns `consume_grant`, not `allow`; the repository must check live revocation/expiry/fence and consume atomically. Scoped recurring permissions require a trusted constrained adapter to materialize an exact-action grant; this contract does not infer merchant/content scopes. Arbitrary shell, browser interaction and MCP calls are not automatically harmless.

RunBudget is shared by parent, children, routed attempts and auxiliary work. It reserves before dispatch and reconciles streamed cumulative usage by reservation identity. Nil model cost means unknown, never zero. Money uses integer minor/micro units with explicit currency for spending. Model cost and purchase caps are separate. Provider-side billing precision and external exactly-once delivery are not promised.

## Memory and document HTTP contracts

All paths below are relative to `/api/studio/bots/{botID}` and use the same authenticated scope selector. - `GET /memory` returns `{memories: [...]}` with optional `category`, `limit` (1–200, default 50), and `offset` (0–1000000, default 0). Empty results are an empty array.
- `GET /memory/search?q=...` returns the same envelope; `q` must be nonempty and at most 4096 bytes, with optional `category` and `limit` (1–200, default 10).

- `GET /memory/{memoryID}` returns one attributed result. `PUT` accepts `{content, category}` and `DELETE` removes it; both return 204. Cross-Bot memory access and team-reader writes are forbidden. Updates preserve the existing session/creator provenance.
- `GET /documents` returns `{bot_id, version, revision, documents: [...]}`. Optional positive `version` selects historical persona/charter; omitted selects current. `GOALS.md` and `goals/<UUID>/GOAL.md` contain current independently revisioned goals/evidence. `MEMORY.md`, `people/INDEX.md`, `groups/INDEX.md` and `notes/YYYY-MM-DD.md` project current attributed memory with `source_version`, `read_only`, `write_unsupported_reason` and per-row `record_mappings: [{id, session_id, expected_fingerprint}]`. Memory projections are bounded to 2000 records and disclose truncation. The combined projection is not an atomic cross-record or historical memory snapshot.
- `PUT /documents/{document}` accepts `{expected_revision, content, reason, confirmed}`. Explicit confirmation, a nonempty reason and revision CAS are required. Only `SOUL.md`, `IDENTITY.md`, `USER.md` and `CHARTER.md` are directly editable; goal and mapped memory documents reject raw Markdown replacement with 503, and unknown names return 400. `ApplyVersion` permits reviewed prose edits in draft/paused/stopped state, inserts the immutable version and persona activity once, and preserves policy, disabled schedules, lifecycle and teardown barriers. Success returns `{bot_id, version, revision, document, activity_kind}`; stale retries return 409.
- `POST /documents/{document}/ingest` accepts a structured `BotMemoryReview`, **not raw Markdown**. Supported targets are `MEMORY.md`, `people/INDEX.md` (person/people categories) and `notes/YYYY-MM-DD.md` (sources from that UTC creation date). Groups, goals, credentials and unknown document paths cannot be imported here. New notes use the document date for `created_at`, while attribution records the actual review time.
- `GET /memory-health` returns `{bot_id, scope, snapshot, review_only: true, apply_supported: true, health}`. `limit` is 1–2000, default 500. The existing health evaluator receives only Bot-prefiltered records; recommendations remain draft, restricted to the current scope and known source IDs, and do not themselves write or verify knowledge.
- `POST /memory-health/consolidate` applies a separately confirmed `BotMemoryReview` with at least two sources per edit. Both apply endpoints return 200 with a durable `BotMemoryReviewReceipt`; invalid input, forbidden sources and stale CAS are rejected without partial batch application.

The shared review body is `{id, expected_revision, reason, confirmed, edits: [{session_id, content, category, sources: [{id, session_id, expected_fingerprint}]}]}`. Optional `kind`/`document` must match the route. There are 1–100 edits and at most 100 sources per edit, with no repeated source identities. The server supplies the actor and inferred attribution; callers cannot assign evidence, ownership or permissions. A scope-local transaction binds the Bot revision, live authority, exact source content/attribution fingerprints, replacement rows, superseded-source markers and one `memory_review` activity/receipt. Source content/evidence is retained, including snapshots in the receipt; exact same-actor retries replay the receipt without reapplying and changed retries conflict. See [reviewed memory](memory.md#reviewed-bot-memory-batches-and-health) for retrieval and transaction boundaries.

`bot.NewDocuments(BotStore)`, `Documents.Load`, `Documents.LoadMapped` and `Documents.Edit` operate only on authoritative records. These documents are **in-memory projections**, not physical home files. Editing prose or ingesting descriptive people notes cannot widen autonomy, budgets, tool permissions, triggers, identity assignments or delivery bindings.

`TestBotPhase2HTTPAcceptance` passed over real HTTP with production routes/tenant middleware and controlled authentication on SQLite. Its `checkBotDocumentHealthHTTP` / `checkReviewedMemoryHTTP` helpers exercise mapped documents, reviewed multi-record ingest, health recommendations, consolidation, source CAS, receipt replay, preserved superseded evidence and unchanged authority in both scopes, alongside CRUD and error/empty-state coverage. `TestBotPausedStoppedConfiguration` and `TestIntegrationPostgresBotPausedStoppedConfiguration` cover inactive prose changes, immutable history, stale edits, revoked old approvals and preserved shutdown barriers. ## Team template HTTP contract

`GET /api/studio/bots/templates?scope=team` lists reviewed team templates with standard Bot pagination; `GET /api/studio/bots/templates/{templateID}?scope=team` reads one. Team scope must be explicit. `POST /api/studio/bots/templates?scope=team` accepts `{expected_revision, reviewed_for_team, definition}`. The definition is an independent, explicitly reviewed/redacted copy; no source Bot ID or private state is copied automatically. Review acknowledgment is required, and the repository rechecks the current team admin/owner role. Expected revision zero creates; a positive revision updates the exact template name using CAS. Publication and its audit record commit together. This is not automatic prose sanitization.

`POST /api/studio/bots/templates/{templateID}/fork?scope=team` accepts `{template_revision, name, idempotency_key}` and creates a private draft for the authenticated user. The repository verifies the private destination belongs to the same organization and user. Only template charter/language, goal suggestions and disabled schedule suggestions carry over; no grants, credentials, histories or enabled bindings do. Exact retries return the same draft while the reviewed source revision remains current; a stale source revision returns 409. Publication and private creation are separate database transactions, not one cross-scope transaction. Template and fork persistence are exercised by the SQLite HTTP reopen test.

## Lifecycle and read HTTP contract

`POST /{botID}/pause`, `POST /{botID}/stop`, `DELETE /{botID}` and `POST /{botID}/restore` require `{expected_revision, reason}`. These use the repository's typed lifecycle transitions, authorization, worker fencing and retention rules; their response is the persisted Bot state, not proof that compute has shut down. Deletion retains history for 30 days and restore returns paused. Invalid transitions and stale revisions return 409. No endpoint here activates work or confirms external cleanup.

`POST /{botID}/read` requires `{sequence}`; the viewer is always the authenticated user. Missing/future/negative sequence values are rejected. Exact or older cursor retries do not generate activity or move the cursor backward.

## Repository persistence encoding

Typed Bot documents are stored in a `bot_document` JSON-string envelope inside
Ent JSON fields. This prevents Ent's generic map decoding from rounding large
integer action IDs or budgets through float64. Indexed identity/status/revision
columns remain authoritative and are checked against document identity on read.
A regression test uses an action identifier above 2^53 and verifies its approval
digest still matches after database round-trip. Plain-map decoding is retained
for root metadata and earlier development fixtures.
