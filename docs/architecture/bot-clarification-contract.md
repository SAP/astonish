# Interactive Bot clarification contract

## Employee-operation evidence boundary — 2026-11-08

Clarification questions remain distinct from operation authorization. Studio and terminal employee-operation controls do not turn assistant prose into a question or grant authority by display. Current UI implementation is not proof of a live provider decision: **LIVE acceptance remains pending**. Historical nine-stage smoke receipts do not validate this newer contract; controlled daemon HTTP and isolated PostgreSQL evidence must be reported separately.

Interactive Bot Chat uses the shared `ask_user` tool for clarification that genuinely blocks the current request. **New title-created Bots must first confirm their assignment**, as described below. After that initial confirmation, the employee does useful clear work first and asks further questions when appropriate, rather than starting a universal onboarding questionnaire. Open-ended missing input uses `kind=text`; meaningful choices use `kind=select` with `allow_custom_answer=true`. The user need not request a tool explicitly.

The instruction is confined to Bot Chat in `pkg/agent/bot_prompt.go` and the trusted initial-title stage. Legacy runs without title-confirmation state, ordinary direct messages, schedules, background work, and ordinary Chat retain their existing behavior. No renderer converts assistant prose into a question card; only a genuine tool result follows the existing shared question/checkpoint pipeline.

## Initial-title confirmation

Personal and team title creation use one focused, genuine `ask_user` select question with three or four distinct title-specific preferences and a custom-answer input. This requirement applies to the new title-confirmation lifecycle, not to generic question validation or every later turn. Initial question generation cannot provision a physical Home, research, perform requested operations, or publish a Task. A validated owner answer binds the confirmed assignment to the same saved run; it does not overwrite the original title or its admission hash. Question generation consumes active budget; waiting for the owner does not.

The existing Studio `QuestionCard` inside `BotReviewCard` renders this question without a new wizard, SSE event, or answer endpoint. It uses the same `w-full max-w-2xl` transcript layout as standard Chat, without a second padded review border or a shrinking flex row. Missing approval metadata shows **Thinking…** and immediately requests a refresh, rather than a saved-review placeholder. The transcript mapper retains a real `chat_question` payload (including its runtime approval reference when supplied), but that display payload never fabricates approval authority: controls require the saved approval and digest. Snapshot pending approvals are merged with the review list so an older empty list cannot hide a newly committed question. Pending options submit their durable IDs; custom answers must be nonblank and within the shared length bound. The custom-answer textarea alone displays `Something else…` as its placeholder and retains `Custom answer` as its accessible name; ordinary text questions keep their own prompt and no added placeholder. An in-flight answer disables all choices and custom submission. Failure retains the question and typed custom details for an exact retry; success removes the actionable pending card and reports that continuation was queued, not that execution already finished. Existing paused-run behavior is unchanged.

Refresh or restart restores the same approval and question IDs; rendering or closing the card must never generate an answer. The canonical ordered run-state/question events remain the source of truth. Read-only viewers and stopped, deleted, or expired reviews cannot submit. Losing access must clear protected workspace data at the owning workspace boundary; a card-level read-only prop disables decisions but is not a data-erasure mechanism. Closing Details or navigating away is not confirmation or run cancellation. Explicit cancellation uses the existing run controls.

The terminal uses its existing option navigation and custom-text entry: Enter first reviews the exact answer and a second Enter submits it. While submission is pending, further Enter presses do not produce another decision. Escape closes the local review without deciding the durable question or canceling the run; the existing “Esc cancels” hint refers to the local review only. Restoration retains the saved question and approval identity. Human-readable answer projection does not modify the persisted owner-answer transport or grant authority.

A validated ordinary clarification answer is continuation of the original owner request, not another authorization ritual. One authenticated approve-and-continue submission verifies the saved question/checkpoint and existing durable mandate against current ownership, membership and policy, even after storage reopens without its original turn registry. Registry-only questions reuse live authority or internally register a narrowed continuation; failed transactions cancel only that new registration. This never changes the durable mandate's reference, source, expiry, constraints or quota ledger. Expired/revoked questions and mandates cannot be revived by answering. Initial title confirmation, tool approvals, plan consent and explicit paused/progress recovery keep their separate rules. Authorization, scoped credentials, external-effect permissions, budgets, and receipts remain independently enforced; neither an option nor private custom details constitute a blanket execution grant.

## Later owner requests after completed work

For interactive turns, the newest owner message defines the requested outcome. Historical title confirmations, their answers, saved Tasks and completed results resolve references and preserve relevant preferences; they must not replace the current request or restart completed research. Assignment-clarification guidance applies when the current turn answers a pending clarification, not whenever a historical answer appears in Home history. A delivery or configuration follow-up reuses the completed work unless fresh research is actually requested or necessary. Scheduling remains model-interpreted through the supported adapter, never keyword-routed or authorized by an old title answer.

`TestBotTitleSchedulingFollowupLatestInputHTTP` exercises isolated personal HTTP title creation → custom confirmation → completion → authenticated scheduling follow-up through the production worker/factory. It inspects the actual controlled-provider request, verifies the newest instruction and previous preference coexist, and reads a durable pending schedule operation bound to the fresh run/owner event while that run is active. No additional external-work call is made. This is wiring and prompt-contract evidence, not proof of real-provider intent selection or eventual worker application; the fixture deliberately does not supply activation policy. Current authorization, operation checks and pending-versus-applied receipt semantics remain unchanged.

## Home-chat delivery and canonical questions

Scheduled updates default to the Bot's own home chat with the existing typed delivery policy and no external bindings. Ask about recipients only when the owner explicitly requests an external destination; external changes still require review.

For future publications, a waiting fallback whose committed approval IDs all resolve to valid `ask_user` interactions on that run is recorded as a suppressed publication receipt rather than appended as another Home message. Waiting state and the canonical question review remain durable. Mixed action approvals, failures, artifacts, changed work and genuine limitations are not suppressed; historical rows are not deleted. `TestQuestionOnlyWaitingPublication` covers that boundary, and `TestBotTitleConfirmedLaterQuestionContinuation` proves initial and subsequent question waits do not append Home reports, then verifies a controlled final answer → friendly acknowledgement → tool sequence in the persisted run transcript. This is controlled wiring evidence, not live-provider judgment or browser rendering proof.

Initial options preserve the title's likely intent and clarify the highest-value missing dimension (such as scope, interests, audience, or constraints). Alternatives are concise, concrete, meaningful preferences on that same dimension, generated from the title without hard-coded organizations or topic templates. They need not be complete executable tasks and must not be forced into a menu of different task formats; distinct intents are appropriate only when the title genuinely leaves the intended task ambiguous. Interpret a selected preference together with the original title and question, not as a replacement task. A title answer may lead to another focused question when consequential details are missing. Once sufficiently specified, the employee briefly says what it will do before the first work tool, without another approval ritual or a post-hoc readiness receipt.

Both Bot transcript stream endpoints project redundant question markers using the existing Chat marker parser and persisted approval identity. The exact runtime waiting publication is redundant only alongside that saved question review; other failure reports, arbitrary prose, and later human input remain visible. Projection never deletes stored rows or changes cursor positions; run diagnostics retain the original history. An exact typed question marker matched to the request's scoped, validated approval is projected at its original persisted row as a reference-only `bot_review` (same row ID/cursor, no copied question payload, no synthetic canonical review identity). Home retains that reference; the saved approval alone authorizes rendering and answering. Studio prefers the earliest exact question anchor or approval reference, suppresses a later review for the same approval, and never moves an answered card behind subsequent Employee messages. Ordinary Chat is unchanged. Studio renders the pending QuestionCard once without duplicated heading or permission-style Deny/pending chrome. Remote terminal clients receive the same projected transport.
