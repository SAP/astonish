# Evidence-bound blocked-work responses

## Outcome and authority

Task completion and valid employee communication are separate outcomes. `BotWorkAccepted` retains its complete original criterion pass requirement and exact deliverable binding. A `BotWorkBlocked` state may instead carry `response_outcome=verified_blocker_explanation`: it records that the exact employee explanation is useful and truthful, **not** that the requested action succeeded. The run remains `partial`, failed/unverified original criteria and unresolved findings remain persisted, and artifacts are not published.

The quality projection carries `response_outcome` and `blocked_response` (`candidate_digest`, exact `text`, runtime `blocker`, and separate model `assessment`). Consumers may present that text as the employee response, but must not turn this outcome into task success, promote artifacts, or substitute the reviewer's findings for the employee text. Legacy quality records omit these optional fields. Accepted work may carry `response_outcome=work_succeeded`.

## Provenance and relevance

`BotChatResources.AssessmentContext` reads current captured-owner email discovery under the existing live authority checks. The assessment snapshot contains only the delivery **state**, not the account address, binding, arbitrary next-step strings, or mailbox credentials. Only bytes directly returned by this runtime-owned callback can construct `candidate.runtime_blockers`. Capture clears preexisting blockers even if the callback is missing or fails. Captured tool responses and model prose cannot establish a blocker; a model review returning a `runtime_blockers` field fails strict decoding. The blocker and corresponding read observation are covered by the candidate digest. The exported persisted field is not a cryptographic attestation: the trust boundary is the runtime-only candidate construction and lease-authorized private work store, not arbitrary caller-supplied work JSON.

The initial adapter supports native owner email transport unavailability. Its reason, administrator action, and scope are fixed bounded runtime text. Bot tools cannot configure this transport; neither approval nor a mailbox fallback resolves it. Discovery unavailable, missing evidence, formatting defects, optional unavailable facilities, and ordinary tool errors are not equivalent blockers.

A separate `blocked_response` section of the **existing** tool-free review verifies both dependency applicability and the employee explanation. It identifies original failed criteria and quotes the original assignment establishing the email dependency. Current conservative support requires explicit email wording in that assignment; it does not infer applicability from unrelated goals, candidate claims, or the charter topic. The reviewer must distinguish requesting configuration now from saving future standards and must reject misleading success claims. This applicability/semantic judgment remains visibly `model_assessment`, not a mechanical attestation.

The review now records a typed `dependency_purpose` (`configure_delivery`, `send`, `save_preference`, or `unrelated`) and an independent `dependency_verdict`. Both are required by the structured-output schema. The exact original action clause is retained in `source_quote`; its semantics are independently judged by the reviewer, not inferred from phrase matching or the extracted scope. `configure_delivery` with confirmed relevance may map a `future_task_definition` criterion because configuring actual delivery now is not merely saving standards. `send` still requires `current_turn`; `save_preference` and `unrelated` cannot establish a blocker. Existing persisted reviews with neither new field retain the former current-turn-only gate; they cannot establish independent relevance for a fallback.

If explanation quality fails, normal bounded correction still applies. After correction ends, `ConfirmedRequiredBlocker` allows a closed, server-owned employee fallback to retain the unavailable-transport reason and administrator action, independently of the rejected explanation. It requires valid work/candidate/review identity, runtime evidence, exact source binding, confirmed dependency purpose and relevance, and failed mapped criteria. The fallback neither copies rejected prose nor claims settings were unchanged or changed. Its typed reason is rechecked against private work at commit, and its immutable text/digest survive publication/reload. An unavailable transport observation alone, unrelated metadata, an absent/invalid relevance review, or legacy combined assessment cannot select this fallback. Runtime error causes continue to use their existing reason instead.

Normal repair continues if any failed criterion is not solely blocked by that dependency, or if the explanation itself is defective. The impossible-work shortcut is eligible only with a satisfied separate explanation assessment, all remaining failed criteria mapped to the required dependency, no rejected citations, no pending controls, no uncertain effects, and no exact-action continuation. The original criteria never change verdict because the explanation passes.

## Persistence and execution boundaries

The controller captures and saves the candidate, reviews it once, then transitions `reviewing -> blocked` with the typed response outcome. It publishes the exact captured employee text as a partial response and does not call production again. There is no additional narration/model call; assessment still has no tools, uses the same owner meter, honors cancellation/authority/budget checks, and retains the existing bounded malformed-JSON retry. A replay of terminal blocked work returns the saved explanation without producing work again.

`ValidateBotWorkUpdate` restricts the response outcome transition and preserves immutable sources/candidate identity. `ValidateBotWorkCompletion`, called inside `validateBotWorkCommit`, requires the exact saved explanation projection, summary text and digest, `RunPartial`, and zero artifacts. Existing lease/CAS, authority, accepted-work, and artifact gates remain unchanged. The optional fields persist in existing work/report JSON envelopes, requiring no schema migration.

## Regression evidence

`TestBotWorkBlockedEmailExplanationSequence` first failed on the previous implementation with three production calls, two repairs, and raw reviewer output. It now checks one production, zero repairs, two total assessment calls (prepare/review), partial status, unchanged failed criterion, exact useful employee text and durable JSON reload. Boundary tests cover forged blockers, success claims, unrelated news continuing normal repair, correction of a defective explanation, and independent correctable defects despite a valid blocker assessment. Capture tests ensure absent, failed, available, and unknown discovery cannot retain forged/stale blockers. Store tests also verify report projection mutations cannot alter the private assessment. Store tests exercise altered summaries/digests/projections, success/artifact promotion rejection, and both personal/team repository commit and reload. Launcher coverage checks captured owner identity and omission of private account/binding data.

`TestBotBlockedExplanationPublicationHTTP` exercises the exact incident wording, `can you update it to send via e-mail too ?`, with c1 deliberately extracted as `future_task_definition`. It first failed with an invalid-assessment fallback, then passed for personal and team HTTP admission, real worker/capture/SQLite/publication, one producer, one review, zero repairs, partial status, Home SSE/replay/history and terminal formatting. A second branch rejects the explanation across the existing two repairs and verifies the administrator-action fallback persists without rejected prose. No email/tool calls are executed. Store and composer tests reject future sends, saved preferences, unrelated email metadata, stale digests, unconfirmed/absent relevance, fabricated quotes and unauthorized fallback reasons; schema tests require both new typed fields.

This implementation does not enable transport, change user settings, send email, restart services, or prove live provider/UI rendering. Formatter integration consumes the quality contract above separately.
