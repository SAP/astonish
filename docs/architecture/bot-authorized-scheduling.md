# Source-authorized schedule operations

The schedule-control runtime is a trusted composition capability, separate from generic operation persistence and manual control-proposal review. Construct it with `entstore.NewBotAuthorizedOperationRuntime`, the current mandate policy resolver, an issuer-policy source authorizer, and candidate readiness checker. Nil callbacks fail closed.

## Authority and capture

`EnqueueAuthorizedOperation` accepts a live worker lease, its source task mandate pin, stable key and a typed schedule create/edit/pause/remove payload. It verifies the lease before exposing canonical source text to the trusted authorizer, then verifies again in its scoped transaction. The source must be an authenticated-owner manual run with an actual user event and matching persisted digest. The issuer authorizer receives canonical plaintext and protected direct-owner-message provenance, not model-provided consent claims. Ordinary natural-language messages need no `schedule_command` envelope. The existing turn model selects a candidate contextually; no regex or second model claims to prove semantic intent. The issuer checks exact own-control tool resources under trusted mandate configuration, while storage enforces bot scope, live source lease, immutable payload and finite quotas. Title-start provenance is distinct and cannot authorize recurrence; missing legacy provenance also fails closed. HTTP does not accept a schedule-grant DTO.

A private immutable `authorized-schedule-grant` record binds source run/user/event/digest, payload digest, schedule-control purpose and captured root revision/version. The original task mandate remains task-purpose. This bounded issuer transition does not issue future scheduled execution pins or expand task permissions. Current membership, revocation, expiry and operator limits are checked again on apply.

Pending operations are immutable outbox revisions with deterministic operation/trigger/job identities. Generic operation creation cannot supply provenance; generic transitions cannot mutate issuer-owned records. Legacy operations without provenance remain readable but cannot enter the schedule executor.

## Owner request versus redundant consent

The effective Bot system prompt, Bot-specific job-scheduling guidance and `schedule_job` description agree: an explicit owner request for recurring work within the current bounded mandate proceeds to the scoped schedule adapter. Use the task and cadence already supplied in conversation. For example, when the preceding task is known, “send this here every minute” needs no second “yes, every minute,” mode questionnaire or generic proposal review merely because output may repeat or be frequent. Home delivery needs no external recipient.

This is model guidance, not an authorization shortcut. Runtime minimum interval, finite budgets, source provenance and exact-operation checks remain authoritative. Clarify genuinely ambiguous tasks/cadences or unknown destinations; honor cost/policy limits and `RequireAuthorization`. External effects still require their own authority; legacy non-mandated review and control-only restrictions remain. A queued operation is not an applied schedule. The prohibition on parsing prose as consent concerns bypassing typed authorization or synthesizing an approval, not refusing a clear owner request to call the guarded adapter.

`TestBotRoutineScheduleConsentPrompt` covers interactive Chat and Home turns plus control-only/background exclusions; `TestSchedulingGuidanceRoutineConsent` covers the guidance override. `TestBotFactoryRoutineScheduleConsent` checks the effective provider system instruction and scoped tool description while preserving the natural user turn. These prompt contract tests do not prove a live model's choice. The unchanged controlled `TestBotAuthorizedScheduleHTTPAcceptance` separately exercises natural-language HTTP admission, pending capture, worker application and zero approvals in both scopes.

## Schedule update protocol

`update_scheduled_job` uses a Bot-specific closed input schema, not the ordinary Chat update schema. Supply the existing `job_id` and at least one **top-level** patch field: `enabled` (boolean), `schedule` (nonempty five-field cron), or `timezone` (nonempty IANA timezone). Omitted fields preserve existing values; explicit `enabled:false` pauses recurrence. Empty/id-only, null, nested-patch, name and instructions arguments are rejected. Internal adapter validation still rejects empty mutations independently of the provider schema. Legacy non-mandated edits remain disabled-save reviews, with enable/disable reviewed separately.

This tool does not change task instructions. A preference-only memory request should capture memory and finish, not rewrite, replace or remove schedules. A separately requested responsibility change needs its supported control operation and existing authorization, not create/remove as a workaround. This guidance does not make pending memory applied or excuse an invalid tool outcome. Application uses the source-terminal and authority barriers below; a later operation receipt never rewrites a failed or partial source report as succeeded.

`TestBotScheduleUpdateProviderContract` exercises the real LiteLLM/OpenAI transport against a local controlled endpoint: the outgoing schema contains the supported fields and requires a patch, and incoming unknown/nested arguments remain intact until executable validation. `TestBotScheduleUpdatePatchBoundary` covers both storage scopes, invalid patches, explicit false, preservation of task/cadence metadata and no mutation on capture. `TestBotPreferenceOnlyScheduleGuidance` covers Chat, Home and background prompts. These tests are not evidence of fresh live model behavior.

## Verified enqueue is not applied scheduling

`botScheduleTools.enqueue` independently calls `ReadAuthorizedOperation` after enqueue. `verifyScheduleCapture` checks the returned operation against the durable pending record, requested payload, mandate, idempotency key and source provenance (including the payload digest). Missing, unreadable or mismatched records produce no trusted outcome. A pending-shaped JSON result or operation ID alone is not evidence.

Only successful read-back records a server-only `bot.ScheduleCapture` in the current call's `ToolOutcomes` ledger. The ledger snapshots the capture and consumes it once; ADK's serialized result metadata cannot create an attestation. The runner checks the run/owner identity, operation ID and pending response status again and rejects receipts mixed with changed-schedule, artifact or next-run claims. This works for direct scheduling calls and `execute_tool` without tool-name success exceptions.

The source report records an unchanged observation with a `bot-operation://<bot>/<operation>` source and a server acknowledgment that the operation is durably queued and pending. That acknowledgment takes precedence over a model's premature “Done” summary. It does not set `Changed` or `NextRunAt`, hide unrelated unverified effects, or assert that the scheduler has changed. The later worker-committed receipt remains the authoritative application result in Home.

Regression coverage: `TestScheduleCaptureLedgerSnapshot`, `TestBotScheduleToolsProviderDurablePending`, and `TestBotScheduleCaptureOutcome` verify the ledger snapshot, independent read-back and runner rejection boundaries. `TestBotAuthorizedScheduleHTTPAcceptance` also checks pending-only source success despite premature model “Done”, and that the linked applied receipt follows source termination.

## Scoped schedule discovery

`botScheduleTools.list` reads only the current Bot's version and bound scheduler rows. All binding checks (owner, Bot, trigger, version) must pass before it records an unchanged observation in the server-only `ToolOutcomes` ledger. The source binds scope, Bot, run and exact function-call ID. Empty results are completed reads, not proof of a pending operation; failed/missing reads do not attest success. JSON returned by a model or same-name tool cannot mint this record. The runner consumes it once through existing read accounting, without a tool-name exemption or changed/next-run claim.

Bot schedule names are generated identifiers, so filter words match case-insensitively across the authorized trigger's task instructions as well as its name, ID and mode. All words must match. This is scoped keyword filtering, not semantic intent authorization; it never searches other Bots or the Bot-wide charter. IDs and result schemas remain unchanged. Filter misses explicitly distinguish no match from no schedules.

`TestBotScheduleListReadOutcome` checks both scopes, exact-call single consumption, empty/unbound reads, failures and binding mismatches. `TestBotScheduleListResponseCannotMintRead` rejects forged JSON and wrong-call observations. The cadence stage of `TestBotAuthorizedScheduleHTTPAcceptance` uses real HTTP admission, factory/runner and worker with a controlled model: filtered list → update using the returned trigger ID → independently read durable pending operation while the original job is unchanged → source termination → applied receipt and enabled two-minute job, with no approvals. Personal uses native calls; team uses `execute_tool`. These are source-level runtime tests, not fresh live-provider acceptance.

## Atomic application

Application waits for `source.Run.Status.Terminal()` and the root ActiveRun barrier to be clear, not specifically `store.RunSucceeded` (`pkg/store/entstore/bot_authorized_schedule.go:162,195`; routine application uses the same terminal predicate in `bot_authorized_routine.go:211`). Terminal state clears a lifecycle barrier; it is neither evidence of a successful source tool nor authority by itself. Source outcome/report and later operation application are distinct durable facts. Readiness evaluates the current Bot and candidate version outside the transaction; both snapshots and the private grant are rechecked before writes. A root CAS fences version/revision/sequence and the no-active-run barrier **before any scheduler mutation**, so concurrent PostgreSQL applicants cannot both insert the deterministic job identity. A losing CAS returns the retryable `ErrBotConflict`; an already-applied replay returns its original receipt. No unique-constraint error is treated as successful application.

Occurrence acknowledgement preserves its exact persisted due-time CAS and changes only runtime fields. Its typed Ent update either sets the next occurrence or clears it, never both (PostgreSQL rejects duplicate assignments).

The transaction writes the immutable version, target scheduler state, optional target-only draft activation, receipt revision and publication intent. Unrelated jobs receive only version rebinding: their effective Enabled and NextRun are retained exactly, including disabled jobs with retained due dates. Paused/stopped roots are never resumed. Readiness or mutation failures leave the queued operation unapplied; retries cannot produce duplicate job identities or receipt intents.

Finite count, minimum recurrence interval and daily frequency bounds are checked over a year-plus-day horizon (including DST); runtime dispatch quota is separately enforced by mandate admission/reservation. Schedule operations cannot smuggle hook credentials, goal bindings, external delivery or configuration changes.

## Queued occurrence reconciliation

Authorized schedule application reconciles already-admitted, unclaimed cron and goal-deadline runs inside that same root-CAS transaction. An edit that changes the trigger (including cadence, timezone or instructions), pause, removal, or effective disabled job cancels its obsolete queued occurrence with a terminal timestamp and durable run-state activity. Older stranded versions are cancelled conservatively rather than assigned today's authority.

An occurrence from the immediately preceding version may be rebound **in place** only when the complete enabled trigger is unchanged, its admitted instructions still match, and its bound scheduler job is effectively enabled at the new version. Only the run version changes: run/session identity, occurrence timestamp, request hash, idempotency/dispatch identity, mandate pin and caller ceiling remain unchanged. No second admission, redispatch or refreshed grant is created. Current policy, expiry, revocation and worker-identity checks remain required before execution.

Started or previously leased records are not repurposed. Claim/admission and reconciliation share the root write barrier; row updates additionally compare version, queued status and empty lease/fence. Manual runs and terminal history are untouched. Unrelated scheduler rows retain their exact effective enabled and next-run state. Queue updates, lifecycle/version writes, sequence allocation, run-state activity and the applied-operation receipt either commit together or roll back together. This is prevention/reconciliation on authorized schedule application, not a startup migration or permission to replay existing live queues.

`TestBotAuthorizedScheduleQueuedReconciliation` exercises due occurrence admission followed by edit/pause/remove/create, cancellation versus unchanged rebinding, disabled unrelated jobs, stale worker rejection, current policy and revocation, duplicate replay, active-lease fencing, and injected receipt failure with run/root/version/scheduler rollback in both SQLite scopes. `TestIntegrationPostgresBotQueuedScheduleReconciliation` covers edit/create/pause/remove, historically disabled unrelated schedules and forced claim interleaving against the guarded disposable PostgreSQL fixture.

## Receipts and publication

The typed schedule receipt records source linkage, observed trigger/job identity, version, removal and effective enabled/next-run state. It is written only after those postconditions are observed transactionally. Existing report publication drains the committed intent after commit and deduplicates its Home event. Reserved-key and applied-operation checks distinguish receipts from ordinary source reports; receipts are not suppressed by a prior conversational reply and never authorize external notifications.

## Boundaries

The daemon installs actual run-bound schedule capture adapters in the mandated catalogue. Only these installed adapters receive verified read/capture classification; generic tools and external effects retain their existing policy. The worker drains pending operations after source completion and checks candidate readiness separately from current-version activation. Future task pins are private, exact schedule bindings and do not inherit own-control resources. No new UI, approval auto-acceptance, or user daemon is introduced. Existing manual proposals and ordinary Home reports retain their behavior. Consumers must report queued versus applied truthfully and must not claim successful scheduling on enqueue alone.
